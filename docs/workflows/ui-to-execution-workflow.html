How to read this guide

Each workflow follows the same chain. The browser owns presentation and short-lived state; the Spring controller translates HTTP; the service enforces business rules and permissions; repositories persist an auditable record; the worker performs browser automation only after a queue claim.

UI event→React route/component→API client→Controller→Service + permission→Repository / worker→Visible state

Source anchors: frontend/src/app/router.tsx, backend/src/main/java/com/megumi/testops/*/api, backend/src/main/java/com/megumi/testops/*/service.

1. Startup and authentication bootstrap

Normal path

  1. Docker Compose starts PostgreSQL, the Spring Boot API, the worker, and the Nginx-served React bundle.
  2. The public readiness route loads without a session and shows backend health.
  3. On a protected route, the auth context reads the access token in memory and calls the current-user endpoint.
  4. The refresh token stays in an HttpOnly cookie. A refresh response replaces the access token without exposing the cookie to JavaScript.

Failure and recovery

  • Expired access token → one refresh attempt, then a preserved return URL to Sign in.
  • Unavailable backend → branded retry state; readiness remains public.
  • Unverified user → signed in but restricted, with a persistent verification recovery link.

2. Project creation and target checking

UI event: the user submits the New project form. The project mutation sends a DTO to ProjectController; the service validates the target origin and creates the membership for the creator.

  1. Project is created as an active definition with a target health of NOT_CHECKED.
  2. Changing the target resets health so an old “reachable” result cannot be mistaken for a new target.
  3. Check connection opens an isolated browser context in the worker boundary. Local development requires both the feature flag and an exact allowlisted http://localhost:<port>.
  4. Docker maps logical localhost to host.docker.internal while preserving the browser URL and same-origin policy.
Blocked is a policy result. It is different from unreachable transport. The UI should tell the user whether to allow the exact origin, start the target, or inspect the Docker bridge.

3. Suite and case authoring

Definition workflow

  1. Project workspace loads suites using an absolute project route.
  2. Creating a suite requires DEFINITION_MANAGE; archived projects/suites reject writes.
  3. The case builder moves through Details → Steps → Review.
  4. DRAFT validation checks only present structure; READY validation additionally requires a first NAVIGATE, complete action fields, supported locator roles, and resolvable variables.
  5. Save draft, Save as READY, and Save & run are single-submit actions with optimistic version protection.

Step language

Action metadata comes from PlatformOptionsController, so the builder does not maintain a second incompatible action list. Each step records action, locator strategy, value/input, expected value, timeout, and optional role/index settings.

A case is mutable until queued. A queued execution uses an immutable snapshot, so later edits cannot change the run.

4. Queue, claim, and execute

Save & run→202 + Location→execution row→worker claim→snapshot browser run
  1. The queue endpoint validates project, suite, case, READY status, target policy, and idempotency key.
  2. The response returns 202 Accepted, { executionId, status }, and a Location header. The frontend navigates to the run detail.
  3. The worker claims a queued row, resolves non-secret variables, and decrypts secret variables only inside the worker process.
  4. Chromium runs the ordered snapshot steps. Main-frame navigations caused by clicks, redirects, forms, popups, and scripts are checked against the approved target origin.
  5. Each step writes status, duration, failure position, and sanitized detail. Retries are bounded by the case definition.

5. Evidence, artifacts, and reporting

Successful screenshot steps persist an image with its step position. Traces remain downloadable when policy allows. Secret-bearing steps suppress eligible evidence and redact values from messages, logs, screenshots, and traces.

  1. Execution detail reads a lightweight summary first, then case results, step results, and artifacts.
  2. Artifact downloads re-check project membership; a non-member receives a non-disclosing denial.
  3. Dashboard endpoints aggregate over the selected UTC window and scope results to accessible projects.
  4. Archived definitions remain readable for history, but cannot be edited or queued until restored.
Maintainer rule: keep the relationship between execution snapshots and mutable definitions. History must explain what ran even after a case is edited, archived, or restored.
