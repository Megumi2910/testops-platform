Before you begin

TestOps is a manager for browser checks. It does not change the target website. You register a target origin, describe steps, and let an isolated Chromium worker execute an immutable snapshot.

Local services

  • TestOps UI: http://localhost:3000
  • TestOps API: proxied by the UI; direct backend is normally http://localhost:8080
  • Optional ecommerce target: http://localhost:3001 when its controlled stack is running

Safe habits

  • Use a QA mailbox and QA-owned records.
  • Never paste tokens, passwords, OTPs, or secret variables into screenshots.
  • Use exact allowlisted origins; do not test arbitrary LAN or private addresses.

1. Check platform readiness

  1. Open http://localhost:3000.
  2. Wait for the green Backend ready card and an UP actuator status.
  3. Select Sign in or Create account.
If the card stays in a loading state, inspect container health and the browser Network panel. A readiness failure is different from an invalid password.

2. Register, verify, and sign in

Who: guestRoute: /registerAPI: Auth
  1. Enter a display name, a QA email, and a password that meets the visible requirements.
  2. Select Send verification code. The server creates an OTP challenge and sends one message through the configured mail provider.
  3. Open the verification page, enter the six-digit code, and submit.
  4. If the code expires, select resend. The server controls the cooldown; do not repeatedly refresh to bypass it.
  5. Sign in. A verified user reaches the workspace; an unverified user remains signed in but sees a persistent verification banner and restricted actions.

Forgotten password

  1. On Sign in, choose Forgot your password?.
  2. Request a reset code. The response is intentionally generic so it does not reveal whether an address exists.
  3. Enter email, OTP, new password, and confirmation.
  4. After success, return to Sign in. Invalid, expired, reused, and rate-limited codes are shown beside the relevant field.

Backend ownership: auth/api/AuthController.java and auth/service. The refresh cookie is HttpOnly and is never copied into a form or report.

3. Use the account menu and security center

Who: signed-in userRoute: /account
  1. Open the top-right account control. It exposes your display name and email plus permitted destinations.
  2. Choose Account security to change a password, add a password to a Google-only account, or manage login methods.
  3. Changing a password requires the current password, a new password, and confirmation. On success all refresh sessions are revoked, so the browser returns to Sign in.
  4. Open Active sessions to review issue time, expiry, user agent, and IP. Revoke one session or revoke all; revoke-all signs out the current browser.
  5. Google linking is shown only when configured. Unlinking requires confirmation and a current password when it is the only remaining login method.
Deep links are shareable inside your own session: /account#security, /account#login-methods, and /account#sessions.

4. Create a project and register a target

Who: verified user with project-management permissionRoutes: /projects, /projects/newAPI: Projects
  1. Open Projects and choose New project.
  2. Enter a unique name, description, and exact target origin such as http://localhost:3001.
  3. Save. The project starts with target health NOT_CHECKED.
  4. Open the project overview and select Check connection. A check records sanitized status, response status, and check time; it does not store page content.
  5. For a local target, enable local development in backend configuration and allowlist the exact origin. The worker maps browser-visible localhost to host.docker.internal.
  6. Use Open target to confirm the page independently. If the check is BLOCKED, fix policy configuration; if UNREACHABLE, start the target or inspect Docker networking.

Project target changes reset health. Archived projects are readable but do not accept definition or execution writes.

5. Create suites and cases

Who: project manager/test managerRoutes: project workspace → SuitesAPI: Definitions
  1. Open the project and choose Suites → New suite.
  2. Give the suite a unique active name. Use the suite description to document purpose and target assumptions.
  3. Choose New case. The builder has Details, Steps, and Review stages.
  4. Select a template: Homepage smoke, Search journey, or Blank case. Templates are starting points; review every locator.
  5. On Details, set name, description, status, priority, tags, retry count, and browser context.
  6. On Steps, add actions. Use semantic locators, explicit values, supported ARIA roles, and a timeout appropriate for the target.
  7. Use duplicate, reorder, and remove controls to refine the sequence. A viewer sees static summaries rather than editable controls.
  8. On Review, save a DRAFT while work is incomplete, or save as READY only after validation passes.

6. Variables and project members

Variables

  1. Open Variables and create a plain or secret value.
  2. Use the variable name in an input, expected value, locator, or navigation URL with the supported interpolation syntax.
  3. Secret values are masked in every API/UI response and decrypted only inside the worker.
  4. Before deleting a variable, resolve reference conflicts reported by the server.

Members

  1. Open Members and invite an existing user.
  2. Select the least-privileged project role needed: manager, test manager, tester, or viewer.
  3. Role changes are version-protected. A final manager cannot be removed or demoted if it would leave the project unmanaged.
  4. Non-members receive non-disclosing responses for nested project resources.

Backend ownership: ProjectVariableController, DefinitionController, and project membership services.

7. Trash, archive, and restore

Who: definition managerRoute: project → Trash
  1. Open a suite or case and select Move to trash. Confirm in the accessible dialog.
  2. The definition becomes read-only and is excluded from active lists. Existing execution history remains readable.
  3. Open Trash to review archived suites and cases with actor/time metadata.
  4. Select Restore. A restored suite preserves child states; an individually restored case returns to DRAFT.
  5. If an active definition now uses the same name, provide a new name and retry. The server returns a structured conflict rather than silently overwriting.
Archive is the deletion model for definitions. Executions are immutable and are not manually deleted.

8. Run a case or suite

Who: member with execution permissionRoutes: case detail or ExecutionsAPI: Execution
  1. Open a READY case and choose Save & run, or queue the suite from its detail page.
  2. The API returns 202 Accepted with an execution ID and a Location header. The UI navigates directly to the run.
  3. Do not edit the case expecting the queued run to change. The worker executes the immutable snapshot captured at queue time.
  4. Watch the status move through queued, running, and terminal states. Polling stops once the run is complete.
  5. Use cancel only as the requester or an authorized project manager. Retry queues a new execution and preserves the original history.
ResultRead it asNext action
PASSEDAll steps met their expected outcomes.Review evidence and keep the case READY.
FAILEDTest assertion or locator did not meet the case definition.Open the failing step and correct the definition or target.

9. Read step results and evidence

  1. Open the run detail and start with the failure category banner.
  2. Review the ordered case results. Each step shows status, duration, failure position, and sanitized message.
  3. Screenshot steps show an inline preview when evidence policy permits. Use the download action for a retained trace.
  4. If a case used a genuine secret, evidence suppression is explained. Values must never appear in the message, filename, screenshot, or trace.
  5. Use the correlation ID when contacting an operator. It links the UI error to server logs without exposing credentials.
A target-unreachable error is not a failed assertion. Start with target health and worker readiness before changing locators.

10. Dashboard and administration

Dashboard

  1. Open Dashboard and choose a 7, 30, or 90-day UTC window.
  2. Filter by project, suite, or browser when permitted.
  3. Use failure cards to jump to the correct execution. Infrastructure categories cover the full selected window.

Administration

  1. Administrators open Administration from the account menu.
  2. Search and paginate users; update role or account status with pending protection.
  3. The server prevents changes that would leave zero active administrators.
  4. Locked or disabled users are re-tested after a status change.

11. Test the ecommerce target safely

The ecommerce site is an external system under test, not a TestOps data store. Start its controlled Compose stack, register http://localhost:3001 exactly, enable the local bridge, and run a smoke case that navigates to /, asserts the catalog heading, and takes a screenshot.

  1. Confirm the ecommerce frontend is reachable from the host browser.
  2. Confirm the TestOps worker can reach host.docker.internal:3001.
  3. Run target check before queueing a case.
  4. Use QA credentials and deterministic local fixtures only.
  5. Keep payments, concurrency, Mailpit interception, and two-user messaging in native ecommerce tests when the workflow needs stronger orchestration.

See the workflow guide for the Docker/browser networking model.
