How TestOps is put together

The UI collects intent, the API protects durable state, and an isolated worker turns approved definitions into browser evidence. Each boundary exists to keep a test result trustworthy when the target, browser, or user changes.

System thesis

The hard part is preserving trust across mutable definitions and asynchronous browsers.

A user can edit a case after a run is queued, a target can become unreachable, a browser can crash, and a secret can appear in a locator. TestOps keeps those events understandable by separating management from execution and by snapshotting the inputs that a run actually used.

Maintainer rule: the frontend may hide controls for convenience, but only backend services and database constraints decide who can mutate a project or what a run means.

Trust boundaries that protect history

Identity versus authorization

Google or password login resolves to one local user. Project membership and effective permissions are evaluated by backend services on every protected operation. A hidden button is never the security boundary.

Definition versus execution

Queueing copies the target, browser settings, case definitions, ordered steps, retry policy, and variable references. Editing a case later changes future runs, not history already queued.

Secret versus evidence

Secret variables remain encrypted until the worker needs them. Resolved secret values are excluded from API responses, logs, failures, screenshots, and traces according to evidence policy.

Target versus platform

Only an exact approved origin is usable. Local development additionally requires an explicit feature flag and the Docker host alias. Private addresses, cross-origin redirects, popups, and form navigations are blocked.

Functional versus infrastructure

An assertion mismatch is a test failure. A browser crash, target outage, worker timeout, invalid definition, or blocked navigation is an infrastructure or policy error with separate guidance.

Mutable versus retained

Projects, suites, and cases use archive/Trash semantics. Execution history and snapshots remain readable so moving a definition to Trash cannot rewrite the past.

Reporting and operational reality

Dashboard flow

The browser sends a scoped reporting window and optional project, suite, and browser filters. The dashboard service performs bounded PostgreSQL aggregates rather than loading every result into Java. UTC date formatting keeps the selected window stable across machines.

Why this matters

A dashboard that mixes inaccessible projects or truncates the selected window creates false confidence. Aggregates and permission scope therefore live server-side, while the frontend owns retryable panel states and URL-backed filters.

Failure recovery

  • Target failure: re-check the target and inspect the target health reason.
  • Invalid definition: return to the builder; the case remains editable.
  • Worker failure: retry only when the case policy and data isolation make that safe.
  • Artifact failure: preserve the primary test result and report the missing evidence separately.
  • Stale route chunk: perform one guarded reload, then show a recovery page.
Deferred by design: scheduled runs, distributed workers, multi-browser execution, permanent execution purge, arbitrary private/LAN targets, and real payment/provider integration are not part of the current first-release boundary.
