    Phase 6 variable snapshot slice

    Queued executions now persist execution-owned copies of project variables and ordered case definitions. Plain values are snapshotted as plain test data; secret values retain AES-GCM ciphertext, nonce, and key version until ExecutionRunService decrypts them inside the worker. Ordered steps and retry count are copied into execution snapshots, so later case edits cannot change a queued run. PlaywrightCaseRunner tracks the configured secret-key set instead of treating every interpolation as secret, so non-secret variables preserve screenshots and traces while secret-bearing steps suppress their evidence. Focused unit tests, the non-integration backend verification, and Compose rebuild passed; Flyway applied V018 and the backend reported healthy.

    The runner also monitors main-frame and popup navigation caused by clicks, forms, redirects, and scripts. Any escape from the approved origin is closed or failed as the sanitized BLOCKED_NAVIGATION category; same-origin redirects and the explicit localhost bridge continue through the shared target guard.

    Execution failures now retain stable categories for assertion mismatches, invalid definitions, locator timeouts, blocked navigation, unreachable targets, browser crashes, and worker timeouts. Case results preserve the category for both test and infrastructure failures while execution-level infrastructure reporting remains limited to worker/target failures.

    The step catalog now also covers keyboard and UI state behavior: PRESS, HOVER, value/checked/enabled/disabled assertions, attribute and count assertions, and exact target-guarded URL assertions. The platform options endpoint is the single metadata source; the guided builder renders only applicable fields and action-specific examples before the same backend validation runs.

    The ecommerce catalog is now source-controlled in catalog/ecommerce-testops.json and synchronized by scripts/sync-ecommerce-catalog.ps1. Stable markers make project, suite, case, and variable updates idempotent; dry-run/apply modes keep secrets out of Git and promote only API-valid cases to READY.

    The synchronizer now performs a fail-closed preflight before any API call. It validates the expanded action/locator catalog, exact text and zero-based locator indexes, required fields, contiguous positions, first-step viewport/locale/timezone settings, READY ordering, and timeout bounds. The homepage smoke manifest demonstrates those context and locator fields, so a malformed catalog fails locally instead of partially updating TestOps.

    Catalog reconciliation is deterministic when a legacy E2E database contains duplicate markers: Resolve-CatalogMatch warns with every matching ID, prefers READY over non-ready definitions, then chooses the highest version. It never lets a stale zero-step draft win silently, and it does not delete records without an explicit API/UI cleanup decision.

    Execution interpolation also exposes immutable generated values: RUN_ID, CASE_RESULT_ID, and RUN_TIMESTAMP. They are inserted by ExecutionRunService after queue-time snapshots, so retries are reproducible and ordinary evidence remains available.

    The E2E topology includes a second isolated disabled-local-target project on frontend :3101, Mailpit :8026, and a separate PostgreSQL volume. Its negative test confirms the same allowlisted localhost origin is visibly blocked when TARGET_LOCAL_DEV_ENABLED=false.

    PlaywrightCaseRunner now resolves variables across locator, input, expected, and navigation fields as one immutable action payload. Missing variables fail closed before Playwright receives the action, while generated run values remain evidence-safe.

    Phase 4 guided-authoring boundary (2026-08-09)

    GuidedCasePage.tsx owns Details → Steps → Review orchestration, React Hook Form owns local field state, and React Query owns create/queue pending state. caseBuilder.ts is the small pure boundary that validates backend-provided action descriptors and maps paths such as steps[2].locatorRole to stable client step IDs. CasePage.tsx reuses that same mapping when an existing definition is edited.

    The backend remains authoritative: the frontend prevents obvious incomplete transitions, but structured problem responses decide whether a definition is valid and unique. Save & run retains the created READY case when queueing fails, then retries only the queue operation. This prevents duplicate definitions and separates durable authoring state from transient worker availability.

    Focused lint, typecheck, 26-test unit, production build, and Chrome DevTools accessibility checks passed. The live check found and corrected missing focus transfer on invalid Name before publication.

    Phase 4 optimistic-lock boundary (2026-08-11)

    CasePage.tsx sends the loaded case version with each update. A 409 stale_version starts a separate latest-case request instead of invalidating the active query, because automatic invalidation would reset React Hook Form and editable steps before the user could compare them. caseConflict.ts calculates visible differences, while CaseVersionConflict.tsx owns focus and explicit Reload/Retry actions.

    Reload updates React Query only after user confirmation. Retry sends the current local definition with the newly fetched version and repeats comparison if another writer wins. Chrome DevTools proved both paths with two authenticated tabs and restored the QA fixture afterward.

    Phase 4 OTP resend boundary (2026-08-11)

    AuthService now serializes verification resend decisions by locking the stable user row before inspecting or replacing an optional challenge. This closes the race in which two eligible requests could both issue and deliver a code. Cooling-down requests are successful idempotent operations: they return the existing retry window and do not create a challenge, send mail, or record a successful resend audit.

    The public controller returns one enumeration-safe 202 representation for unknown, verified, cooling-down, and eligible addresses. VerifyEmailPage consumes retryAfterSeconds, announces the generic status, and disables its accessible resend button. Chrome DevTools and the QA Mailpit overlay proved that two simultaneous cooldown requests leave the mailbox at one registration message.

    The first CI run exposed stale browser copy assertions rather than a product failure. The corrected Playwright recovery flow uses a bounded observation window for any resend response after reload and checks Mailpit remains at exactly one message whether the UI suppresses the repeat or the backend accepts it idempotently, making side-effect safety—not wording—the release contract.
