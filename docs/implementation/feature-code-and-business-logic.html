How to navigate the source

The backend is organized by feature rather than by technical layer alone. A request enters an api controller, is validated and authorized in a service, and reaches a repository through a transaction boundary. The frontend mirrors that mental model with route-level feature folders, API clients, query hooks, and focused forms.

React route→query/mutation hook→HTTP client→Spring controller→service transaction→repository→DTO response

Use exact source paths in this page as search anchors. They are intentionally more useful than a large pasted code listing.

Core syntax and patterns

Java and Spring

  • Records such as request/response DTOs make immutable transport data explicit and prevent entities leaking over HTTP.
  • Annotations such as @RestController, @RequestMapping, @Transactional, and validation annotations declare framework boundaries.
  • Constructor injection makes dependencies visible and testable; services receive repositories and policy collaborators.
  • JPA repositories express scoped queries while services enforce ancestry and permission before calling them.
  • Flyway migrations are append-only; the current schema is V001–V023.

React and TypeScript

  • Hooks such as useQuery, useMutation, and useForm keep server state, mutation state, and field state separate.
  • Lazy routes reduce the initial bundle; Suspense and chunk recovery provide the loading/error boundary.
  • Zod mirrors user-facing validation, but the backend remains authoritative.
  • Semantic controls (links, buttons, labels, dialogs) preserve keyboard and screen-reader behavior.

Feature ownership and business rules

Authentication and account security

User intent: register, verify an email, sign in, recover a password, manage sessions, and link identities.

Frontend: frontend/src/features/auth, frontend/src/features/account, router entries in frontend/src/app/router.tsx. The auth context owns the access token and exposes current-user state; presentation components call focused mutations.

Backend: backend/src/main/java/com/megumi/testops/auth/api, auth/service, auth/repository, and domain entities. Passwords are hashed; OTPs are purpose-bound and rate-limited; refresh sessions are revocable.

Preserve: refresh cookies remain HttpOnly, generic reset responses avoid account enumeration, unverified users can recover verification but cannot perform verified-only actions, and password/identity changes revoke sessions.

Projects, memberships, and targets

User intent: create a workspace and safely point it at a website.

Frontend: frontend/src/features/projects owns list, detail, edit, target-health, tabs, Trash, and member screens.

Backend: project/api/ProjectController.java, project services, member policy, and target-check service. Every nested operation verifies project ancestry before looking up a suite or case.

Preserve: exact allowlisted origins, local-dev opt-in, target-health reset on target changes, active-only names, and non-disclosing 404 responses for mismatched identifiers.

Suites, cases, and guided authoring

User intent: describe a repeatable browser check without writing code.

Frontend: project feature routes and builder components. Backend-provided action metadata drives conditional fields and supported roles.

Backend: project/api/DefinitionController.java plus case/suite services and repositories. DRAFT validation checks present structure; READY validation requires a non-empty executable sequence beginning with NAVIGATE.

Preserve: optimistic versions, one-submit save modes, dirty-navigation protection, archived read-only behavior, and static viewer summaries.

Variables and evidence policy

User intent: reuse environment values while keeping credentials out of evidence.

Backend: project/api/ProjectVariableController.java and encryption helpers. Plain values can be interpolated; secret values are decrypted only in the worker.

Worker: execution variable resolution marks a run as secret-bearing and suppresses eligible screenshots/traces while sanitizing messages.

Preserve: VARIABLE_VIEW and mutation permissions are enforced server-side; APIs never return decrypted secrets.

Queue and browser execution

User intent: run a READY case and inspect exactly what happened.

Frontend: execution list/detail routes poll only non-terminal runs and render ordered step outcomes and artifacts.

Backend: execution/api/ExecutionController.java, execution services, repositories, and the worker. Queueing captures target, browser, case, ordered steps, and variable references into an immutable snapshot.

Preserve: 202 + Location semantics, requester/manager cancellation, idempotency, main-frame navigation safety, per-step duration/status, and artifact authorization.

Dashboard and administration

User intent: understand quality trends and manage platform users.

Frontend: dashboard and admin feature routes with independent loading/error states.

Backend: dashboard/api/DashboardController.java aggregate queries and auth/api/AdminUserController.java administration services.

Preserve: full selected-window infrastructure categories, tenant scoping, bounded recent-failure queries, explicit USER_ADMINISTER, and last-active-admin protection.

Validation and error mapping

Errors are intentionally structured so a form can focus the correct field instead of showing a generic banner.

Tests that protect the design

  • Auth and service unit tests protect password/OTP/session rules.
  • PostgreSQL integration tests protect migration shape, active-only uniqueness, archive/restore, snapshots, and step replacement.
  • MockMvc tests protect permission matrices and problem contracts.
  • Frontend tests protect builder validation, pending states, route guards, and account flows.
  • Playwright/Chrome DevTools checks protect the user-visible journey and evidence experience.

When changing a feature, update its request DTO, service rule, route/manual entry, API catalog, and the corresponding test. Do not “fix” a backend rejection only in the UI.

Maintainer checklist

  1. Find the route in frontend/src/app/router.tsx.
  2. Find the API client and query/mutation hook in the owning feature folder.
  3. Find the controller mapping and DTO.
  4. Trace the service transaction and permission helper.
  5. Check the repository query for project/user scope.
  6. Check the Flyway migration and optimistic version fields.
  7. Update the API catalog and affected HTML docs.
  8. Add or update a native/API/browser test.
  9. Run docs verification and inspect screenshots for secrets.
