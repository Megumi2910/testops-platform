# Phase 9 browser quality and performance implementation

Phase 9 adds the repeatable browser-quality contract required before the final
release gate. `frontend/e2e/accessibility-matrix.spec.ts` runs a verified
TestOps account through the public and authenticated shell routes at
`1440×900`, `768×1024`, and `320×800`.

The matrix is deliberately split into six stable contracts:

- critical-route navigation and no horizontal overflow;
- account-menu and mobile-drawer keyboard focus behavior;
- native form validation and structured login errors;
- account and mobile navigation dialogs, including Escape handling;
- the shared automated accessibility helper; and
- route-level PerformanceObserver measurements for readiness, projects,
  dashboard, and account.

The test writes only a sanitized ignored sidecar at
`artifacts/browser-evidence/inputs/accessibility-matrix-result.json`. It does
not persist cookies, request bodies, user data, screenshots, or traces.

The Chrome DevTools companion capture is kept in
`artifacts/performance/chrome-lighthouse.json` and records the public
readiness route at desktop and narrow-mobile emulation. The
`record-p9-performance.ps1` and `verify-performance.ps1` scripts combine and
validate that Lighthouse/trace anchor with the twelve Chromium route records.
The release thresholds are accessibility ≥95, LCP ≤2500 ms, and CLS ≤0.1.

The public readiness Lighthouse/trace anchor is intentionally not presented as
an authenticated-route Lighthouse claim. Authenticated critical routes are
covered by the sanitized Chromium performance matrix; the DevTools capture
provides an independently observed desktop/mobile threshold check without
exposing session material.

Related contracts are the sanitized P9 browser manifest generated by
`scripts/generate-p9-browser-evidence.ps1`, the strict browser-evidence schema
validator, the defect-ledger validator, and the milestone-ledger validator.
